# 分析テンプレートを作る

分析テンプレートは、同じ種類の案件で繰り返し使う判断基準・手順とレポート雛形である。
analysis-frameworkが参照する `skills/analysis-templates/` に集約する。
たとえばモデル評価では、比較方法や禁止するデータ利用をテンプレートで定め、
許容できる誤差など案件ごとに変わる値は、分析開始時の質問として残す。

## 適用条件を決める

依頼や既存の試行から「何を判断するための分析か」「どんな入力があると使えるか」を整理する。
`skills/analysis-templates/SKILL.md` の一覧を読み、同じ目的のテンプレートがあれば、
適用条件と出力を比較して改訂先を選ぶ。
特徴量選択、モデル改善、チューニング、モデル評価、EDAなどの名称は手掛かりに使い、
実際の問いと必要な証拠に合わせて範囲を定める。

## 評価基準と判断者を詰める

資料や既存コードから分かることは先に調べる。残る選択のうち、後の判断の前提になるものから、
推奨案と理由を添えて少数ずつ利用者に尋ねる。特に次の点を明らかにする。

- **評価基準**　何を何と比較し、どのデータと手順で判定するか。可能なら指標・単位・閾値・その根拠を定める。
  閾値が案件ごとに変わる場合は、誰がいつ決めるかを書く。定量化が難しい場合は、判断材料となる観測を示す。
- **判断者**　基準ごとに、エージェントが判断できる範囲と、利用者が自分で判断したい点を区別する。
  利用者に委ねる判断には、提示する証拠、尋ねるタイミング、回答が得られるまで保留する行動を対応づける。
- **制限・禁止事項**　使えるデータ、手法、時間・計算量の上限と、禁止する操作を明記する。
  禁止事項に抵触する試行は除き、残る方法で問いに答えられるかを判断する。

たとえばモデル改善であれば、「同一の検証データで基準モデルとの差を計算する」はエージェントに任せられる。
「推論時間の増加を許容して採用するか」を利用者が判断したい場合は、両モデルの精度差と推論時間を提示する。
採用判断を委ねられるかどうかは、テンプレート作成時の対話で確かめる。

## テンプレート集へ追加する

参照文書の作成先は `skills/analysis-templates/references/<テーマ名>/guide.md`。
目的と適用条件、必要な入力、適用時の質問、評価基準と判断者、制限・禁止事項を記す。
詳細が長くなる場合は同じテーマのディレクトリに分け、guideから読むタイミングと参照先を示す。
テーマ固有のデータ利用制約・停止条件はguideに定め、frameworkがその条件を適用できるようにする。
案件固有の値は質問として残し、分析の実行・対話・記録・終了判断は `analysis-framework` に保つ。

`skills/analysis-templates/SKILL.md` の一覧に、使う場面、必要な入力、guideへの相対リンクを追加する。
テンプレート集の `allow_implicit_invocation: false` を維持し、frameworkから参照できることを確認する。

特徴量選択、モデル改善、チューニング、モデル評価などのモデリング用テンプレートでは、
データ利用と最終評価のルールをテンプレート内に定める。初回の質問に、探索に使えるデータと
最終ホールドアウトの境界・分割規則を含める。開発データ内の分割は目的に応じて選べるようにし、
どの探索結果が方針を支持すれば最終評価に進むかを案件ごとに定める。候補不採用や根拠不足の場合は、
ホールドアウトを未使用のまま理由を報告する。最終評価に進む場合はモデルと評価手順を固定し、
ホールドアウト評価後は報告して終了することを、再開時にも確認できるように書く。
レビューでは「開発段階で候補を見送った場合」と「最終評価で期待以下だった場合」の両方を当てはめる。

`skills/analysis-templates/assets/<テーマ名>-report.md` に出力レポートの雛形を作り、
guideの「出力レポートを作る」から相対リンクで参照する。目的は、分析の知見を伝え、
生成AIが結論に至った判断を利用者が効率よくレビューできるようにすること。

- テーマごとに大章の名前・役割・読み順を固定し、小見出しと段落は案件に合わせて組み立てる。
  冒頭で結論を示し、本文はそのテーマの判断過程に合う順序にする。チューニングなら、
  データや診断の観測、調整の意図、検証結果、判断をつなぐ。結論から根拠へは参照で辿れるようにする。
- 結論を左右する判断には、適用した基準、代表値や図表、解釈、重要な反証・限界を対応づける。
  本文に必要な情報と、各ループの詳細へリンクする情報を決める。
- 見送った分岐は、結論への影響に応じて短く触れる。誤った除外や見落としが最終候補の選択を
  左右している場合は、その判断も本文で確認できるようにする。
- 必須・条件付き・任意の内容と、未実施・根拠不足の場合の記し方を雛形に含める。
  数値や閾値は案件ごとの値を記入できる形にし、雛形の例を採否基準として固定しない。

[共通方針](../../../skills/analysis-framework/references/deliverables.md)を踏まえ、
代表的な案件で、結論から主要な判断・証拠・前提まで辿れるかを確認する。
モデリングでは最終評価を実施した場合、候補を見送って未使用の場合、
最終評価が期待以下だった場合を当てはめ、大章を保って説明できるか確認する。

繰り返す計算や検証にコードが有用なら、`skills/analysis-templates/scripts/<テーマ名>/` に同梱する。
guideからスクリプトを相対パスで参照し、用途、入力、出力、必要な依存関係、実行例を示す。
作業ディレクトリに依存しないよう、参照元の文書を基準にスクリプトの場所を解決する。
追加・変更したスクリプトは小さな入力で実行し、実際の出力を期待値と照合する。

最後に、想定案件を一つ当てはめて、適用可否、最初の問い、評価に必要な証拠、誰がどう判定するか、
制限に抵触した場合の扱いが読み取れることを確認する。作成先と検証結果を報告する。
