# 分析を進める

目的・判断基準の整理から、試行、記録、最終レポートまでを進める。
このスキルは分析の実行・対話・記録・終了判断と成果物のつながりを扱う。
下の選択表から専門Skillを選び、方法・データ利用範囲・終了条件・レポート雛形を進行に取り入れる。
モデルの新規構築・改善、範囲を指定した設定比較・特徴量設計は[modeling](../modeling/SKILL.md)へ渡す。
分析の入口はanalyzeとmodelingとし、専門Skillは必要なものを読む。
専門Skillから共通記録だけを参照する場合は、そのSkillの進行・返却先を保つ。
Python、SQL、Notebookなど、案件の既存環境に合う実行手段を選ぶ。
Pythonで図を作るコードを書くときは、[inquiry-lab-api](../inquiry-lab-api/SKILL.md)で利用できる関数と入力条件を確認する。
設定や結果のJSONを閲覧する際は、`inquiry-lab json inspect <ファイル>` を使う。
ネストは展開されないため、必要な階層を `--key model.params` または `--key model --key params` で指定する。
キー名にドットを含むJSONは未対応。表示の省略や読込範囲は[CLIの説明](../../README.md#jsonの基本確認)を確認する。

## 1. 分析目的を受け取る

「誰が、何を判断・理解できるようにするか」を一文で捉える。方法が先に指定されている場合も、
その方法で答えたい問いを確かめる。既存分析の再開では、現在の答え、関連するrun、前回の停止理由を
確認し、新しい証拠や指示で見直す必要がある判断から再開する。
再開時・compaction後は[全体状態の更新と復元](references/state.md)に従い、`state.json`を最初に確認する。
全体目標・終了条件と現在の個別作業を区別し、古いstateは最新の指示・履歴・原本と照合して更新する。
依頼文書、`作業履歴.md` の現在地と依存関係、関係する記録のJSON・詳細、保存済みの結果を読む。
履歴が古い場合はJSONから再生成する。未実行の計画と実測結果を区別し、再開に必要な証拠が欠けていれば
その不足を明示する。再開時も、依頼と選んだSkillのデータ利用制約・停止条件を確認してから
追加の調査や試行に進む。すでに停止条件を満たしている場合は、その条件に従って総評から続ける。

## 2. 対話で問いと判断基準を詰める

目的と入力から専門Skillを選び、その `SKILL.md` を読む。今回の探索範囲・判断基準・終了条件を依頼に記す。

| 目的・入力 | 使うSkill | 進め方と出力 |
|---|---|---|
| モデルを構築・改善する、または設定・特徴量を変更して比較する | [modeling](../modeling/SKILL.md) | 依頼の範囲に沿って構築・改善・比較を進める。このSkillの一般ループは重ねない |
| 学習済みモデルと評価結果・変更履歴から性格を把握する | [models-understanding](../models-understanding/SKILL.md) | 必要な診断と帰納的な見立てをrunにまとめて返す |
| データの全体像や指定した関心を調べる | [eda](../eda/SKILL.md) | 計画した観察を一括で行い、run結果を返す |
| 観測から次の問いを選び、EDAを繰り返す | [eda-loop](../eda-loop/SKILL.md) | 各回を新しい子へ委任し、知見を統合する |
| 生成条件が分かる予測・正解・照合キーがあり、誤差を診断する | [error-analysis](../error-analysis/SKILL.md) | 対象と方法を先に決め、一括診断を報告する |

`eda-loop` は各回を独立したサブエージェントへ委任する。
委任できない環境で同一エージェントによる反復へ置き換えない。反復の指定がないEDA依頼は1shotで返す。
EDA側からこのanalyzeを使う場合は、その選択を保つ。データと目的に合う見方の参照は `eda` に集約する。
該当するSkillがない場合は、答えたい問い、対象と範囲、使えるデータ、何が分かれば十分か、時間や費用の制約を押さえる。

未知のテーマで得た質問や判断基準に再利用の価値がある場合は、そのテーマと適用条件を添えて
テンプレート候補にする。テンプレートの文書化は別の作業として扱い、今回の分析はそのまま進める。

データを調べる前に、依頼と選んだSkillに基づく利用範囲・禁止事項を確認し、曖昧なら利用者に尋ねる。
その範囲で調べて分かる事実は自分で確認する。利用者の判断が必要な論点は、前提が決まったものから少数ずつ、
推奨案と理由を添えて尋ねる。最初の試行の目的と範囲が定まれば進み、結果を見て決める事項は保留する。
計画だけの依頼なら、ここで問い、判断基準、試行案、未決事項を返す。

望む成果、問いに答えるために必要な証拠、停止条件を区別する。定量化できる場合は、指標、比較対象、
閾値とその理由、評価方法、不確実性を具体化する。基準の根拠が足りないときは、設定に必要な情報を示す。
判定に使う結果を見る前に基準を記録し、探索結果から基準を変更した場合は、以前の基準・変更理由・
すでに見た証拠を残す。

### 分析先と記録を準備する

計画を実行に移す前に、[成果物の共通方針](references/deliverables.md)と
[履歴JSONの記録手順](references/history-recording.md)を読む。依頼、短い作業履歴、各ループの詳細、
最終レポートの保存先を揃える。

新規の分析先を作る場合は `inquiry-lab init <新規ディレクトリ> --title "分析タイトル"` を使う。
最初のrunがEDAなら `--template eda` を付ける。
既存の分析先はそのまま使い、再度initしない。依頼・目的・判断基準・判断者・データ利用範囲・制約を
`requests/001-initial.md` に記す。既存案件で依頼文書が別にある場合は、その文書を参照できるようにする。
案件に適用するSkillとレポートの雛形も決めておく。
実行前に[全体状態の手順](references/state.md)を読み、`state update`で`state.json`を保存する。
個別作業の開始前と判断後に更新し、委任した子の結果も親が全体の状態へ反映する。

追加のrunは `inquiry-lab run new --workspace <分析先> --title "試行タイトル"` で準備する。
CLIが番号を割り当て、作成したrunの絶対パスを返す。その保存先とresult.md内のrunラベルを以後の記録に使う。
EDAなら `--template eda`、初期依頼以外に対応するなら `--request <依頼文書>` を付ける。
依頼文書の相対パスは分析先を基準にする。作成済みrunの再開ではこのコマンドを使わず、既存の記録を引き継ぐ。

CLIはrunの採番・雛形作成と履歴の記録・文書生成を担当し、分析の実行、採否、完了は管理しない。
CLIが使えなければその制約を伝え、許可された保存先に同じ形式の記録を残す。
未導入のCLIが正常に保存・生成したとは扱わない。

## 3. 分析ループを進める

`models-understanding` は今回の性格把握をrun結果にまとめて返す。一般ループと4節の統合レポート作成は重ねない。
`eda` では計画した一回の観察をrun結果と成果物に保存して完了し、以下の継続・分岐や4節の統合レポート作成へ進まない。
直接実行でも `output.md` は執筆・更新しない。統合は呼出元が担当する。
`eda-loop` では各 `eda` の呼び出しを試行として記録し、次の依頼・継続・停止は `eda-loop` の手順に従う。
この節の一般ループを重ねて回さない。各回の観察は子が担当し、共有履歴と統合レポートは親が更新する。
`error-analysis` は計画した診断を実施・記録したら4節の総評へ進み、結果から新しい切り口を追加しない。
それ以外の分析では、選んだテーマの制約・停止条件を優先し、以下を使う。

1. **試行の問いを選ぶ。** 目的に照らして不足している証拠を特定し、次のrunで答える問いを一つ選ぶ。
   どんな結果なら現在の答えや行動が変わるかを示し、過去の試行との重複、実行可能性、費用を考慮する。
2. **分析を実施する。** 問いに合う方法を選び、一まとまりの試行を一つのrunとして扱う。
   予定と実施した内容を区別し、失敗した試行も理由とともに残す。
3. **結果を評価する。** 実際の出力を判断基準に照らし、支持・反証する証拠と限界を確認する。
   過去のrunとも比較し、何が観測され、何が解釈で、どこに不確実性が残るかを示す。
4. **終了を判定する。** 問いに十分答えられたか、残る制約の中で答えを変えうる追加試行があるかを判断する。
   依頼と選んだSkillの停止条件を優先し、条件を満たしたら総評へ進む。
   同じ問いを続ける、手法を修正する、関連する別の問いへ分岐する、探索を止める、のいずれかを選び理由を残す。

次の試行へ進む前に、問い・実施条件・結果・解釈・次の判断を履歴JSONへ記録する。
各runは一つの問いと判断に対応させ、一括探索の候補ごとに履歴を増やす必要はない。
候補別の設定・指標・失敗は原本に残し、候補の選び直しなど独立した判断が生じたところでrunを分ける。
基準変更や利用者の選択など、試行を伴わない判断は `kind: "decision"` として記録する。
試行の仮説や計画は実行前に残し、結果を見て書き換えた動機と混同しない。
区切りや中断、利用者への提示前には履歴と詳細を再生成し、現在地・未解決の点・次の作業を残す。
反映済み履歴番号、全体の終了条件の充足状況、個別作業と次の行動を`state.json`へ揃える。

目的・対象範囲・予算を大きく変える必要が生じたら対話に戻る。予算には評価と総評の時間も含める。
追加試行の価値が低い場合や利用可能な情報を調べ尽くした場合は、未解決の点を示して総評へ進む。

## 4. 総評を作成する

元の目的に立ち戻り、問いごとに現在の答え、判断を支える証拠、重要な留保をまとめる。
詳しい手法や試行経過は該当するrunを参照する。望んだ成果が得られなかった場合も、
証拠から答えられたことと、判断を保留したことを区別する。
停止理由と、何が得られれば再開する価値があるかを示す。

[成果物の共通方針](references/deliverables.md)と、適用するテーマの出力手順・レポート雛形を使い、`output.md` を作成・更新する。
テーマごとの大章を保ち、小見出しを案件の判断に合わせて組み立てる。雛形がない場合は共通方針の構成例を使う。
共通の進行手順をそのままレポートの章にせず、結論を支える判断を複数runから統合する。
判断に必要な値・図表と重要な反証は本文に置き、当時の判断理由は各ループの詳細、再現用の出力は原本へつなぐ。

提出前に、問いへの回答または保留理由、主要な結論から判断・証拠への参照、原本との数値の一致、
履歴の現在地と停止理由の一致を確認する。未使用のプレースホルダーは取り除く。
最終レポート、作業履歴、必要な成果物への入口と、残る判断・制約を利用者へ示す。
