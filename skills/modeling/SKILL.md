# モデルの構築・改善を進める

現在のデータでモデルを作り、何を使って予測し、どこでどう間違うかを理解する。
初期構成と利用できる知見を出発点にし、新規モデルでは粗い初期調整を行う。
広い仮説探索と深掘りを繰り返し、結果から全体の見立てを更新して、合意した時間・範囲の中で改善を進める。
全体の進行・採否・終了判断を担当し、個別の観察・比較・診断には専門Skillを使う。
設定比較・特徴量設計の範囲が指定されている依頼は、既存のモデル・評価・診断を引き継ぎ、
[parameter-tuning](../parameter-tuning/SKILL.md)または[feature-design](../feature-design/SKILL.md)でその範囲を実施する。
必要な比較条件を揃えたら個別作業へ進み、指定範囲の結果を報告して終了する。

## 入力と記録を揃える

用途、予測対象・時点、入力の利用可能時点、データの版・範囲、評価指標・分割、計算予算を確認する。
今回使える時間または終了時刻を依頼に記し、結果の確認と報告に使う時間も含める。
改善目的と既知の問題を受け取る。評価性能の向上、特定条件の誤りの改善、運用負担の軽減など、
何を良くしたいかと、維持したい性能・制約を依頼に残す。状況確認は既知の情報を中心に行う。
既存のモデル・特徴量・コード・試行結果があれば参照し、資料から分かることは自分で確認する。
学習前の調査は、意味のある学習・評価を始められる範囲にする。
[評価設計](../parameter-tuning/references/evaluation.md)で比較条件を揃え、前処理は学習部分で学習する。
開発データと最終ホールドアウトの範囲・利用履歴を確認し、下の方針で扱う。

新規の分析先は `inquiry-lab init <分析先> --title "タイトル"` で用意し、既存の分析先・未完了runは引き継ぐ。
追加runには `inquiry-lab run new --workspace <分析先> --title "タイトル"` を使い、返された保存先を使う。
依頼へ目的・今回の範囲・制約を記し、[履歴](../analyze/references/history-recording.md)と
[state](../analyze/references/state.md)の共通手順で開始・判断・中断時の記録を揃える。全体の進行とstateはmodelingの担当者が持つ。
stateは共通のschema version 1を使い、個別作業は一つずつ進める。
開始・再開・委任時は [modelingの状態管理](references/state.md) に従い、採用中のモデルと今回の対象を区別する。

## データの利用方針

モデルの構築・改善と、それに使う専門Skillに共通するデータ利用方針とする。
全体進行担当が利用範囲と履歴を専門Skillへ渡し、最終評価・再評価へ進む判断を行う。
委任された比較・診断は依頼の範囲で実施し、単独実行ではその担当者が依頼の範囲内で判断する。
初期AVは構築・改善を始める際に検討し、範囲が決まった比較・診断では既存の分布差の所見と利用履歴を引き継ぐ。

- **最初に分布差を把握する。** 軽く学習できる場合は、予測モデルを作る前にアドバーザリアルバリデーション（AV）を行う。
  開発データと最終ホールドアウトの入力から出所を分類し、AV自身の検証性能と重要度で違いを調べる。
  識別性能は既存のROC図、スコアや特徴量の分布は出所で色分けしたヒストグラム・箱ひげ図で確認できる。
  予測対象の正解は使わず、出所を直接示す管理用の列は除く。入力分布を参照した範囲を記録する。
  分布差だけで特徴量を削除せず、予測モデルの依存と合わせて懸念を整理する。
  費用やデータ利用条件からAVを行うか判断できない場合は、未決事項と推奨を添えて利用者に確認する。実施できない場合は理由を残す。
- **開発データ内で反復する。** 学習用・開発評価用の役割を保ち、同じ範囲でEDA、診断、特徴量変更、設定比較を繰り返せる。
  開発評価への過適合リスクを受け入れ、その成績を候補選定の証拠として扱う。試行ごとに未使用データを要求しない。
  時系列の順序と予測時点の情報利用を守り、前処理は各学習部分で学習する。
- **最終評価・再評価へ進む理由を別に判断する。** 開発結果とAVで見えた懸念への対応を整理し、候補・再学習手順・評価方法を固定して評価する。
  最初の評価までホールドアウトの正解と予測性能は改善判断に使わない。期待以下でも各回の結果を残す。
  結果を受けて変更する場合は、学習・検証データで変更を裏付け、今後にも有効と考える理由と再評価の目的を記録してから、同じホールドアウトを再利用できる。
  正解を再学習に取り込まず、変更の比較は開発側で行う。再利用の過適合リスクは残るものとし、未使用データによる独立評価とは区別する。

利用履歴は入力分布の参照と正解・性能の参照を分け、最良値だけでなく全評価とその前の判断を保存する。
AVは分布差の診断材料であり、予測性能や再利用の安全性の保証にはしない。最終評価用のデータがなければ開発結果として報告できる。

## 現在地のモデルを作って理解する

1. **学習・評価する。** trainで学習した同じモデルをtrain・validに適用し、それぞれの性能と予測を保存する。
   trainは学習側、validは開発評価側として、性能水準と両者の差を確認する。
   構成がなければ、意味を直感的に説明でき、集計・実装・運用の負担が小さい特徴量と簡単なモデルから始める。
   新規モデルでは、影響が大きいと考えるパラメータを最大3個、各最大2値選び、最大8組の粗いグリッドサーチを行う。
   選ぶ設定・値と理由を先に記し、特徴量・分割・指標を揃えて開発データ内で一件ずつ比較する。
   全候補の結果と失敗、選定理由を保存し、以後の特徴量設計に使う基準設定を決める。
   既存モデルの更新では、設定・評価結果を引き継げるならこの探索を省略できる。引き継ぐ根拠と評価条件の違いを記す。
   学習費用が大きければ小規模なデータで初期比較し、その範囲を残す。実施できない場合は未完了として理由を返す。
2. **モデルの性格を把握する。** [models-understanding](../models-understanding/SKILL.md) に、
   改善目的、構成・評価結果、過去の変更履歴、データ利用範囲と今回の確認範囲・予算を渡す。
   構成・性能・入力依存と変更への反応から帰納的に得た見立て、未確認事項と次の候補を受け取る。
   誤差分析は理解に必要な範囲で使い、次の行動はこのmodelingで選ぶ。

Pythonで図を作る際は[inquiry-lab-api](../inquiry-lab-api/SKILL.md)で利用できる関数を確認する。

## 仮説を作る

利用者の仮説があれば材料にし、エージェントもデータ・モデルの観測から候補を作る。
利用できる検索や永続ナレッジベースも使い、関連する研究・業務知識・過去の成功と失敗から着想を得る。
確認済みの情報は再利用し、情報源が使えない場合は利用可能な材料で進める。特定のサービスへの依存は設けない。

- **出所と適用条件：** 利用者の経験、今回の観測、外部資料、過去の試行を区別し、参照と今回へ適用できる理由を残す。
  外部での成功は今回の有効性と同一視せず、利用者案とエージェント案を同じ比較基準で扱う。
- **期待と比較：** 何を変え、どの対象で何が変わると考えるか、支持・反証する結果、比較方法を記す。
  性能以外の表現上の利点は[特徴量設計の採用基準](../feature-design/SKILL.md#入力と判断基準)に沿って具体化する。
実施前の仮説をrunへ残し、結果を受けた見立ての変更と区別する。
再開時は保存済み候補と新しい証拠から見直す。

## 広さと深さを繰り返す

1. **広く仮説を探索する。** データ・モデルの観測と既存の知見から、異なる観点の改善仮説や表現候補を考える。
   必要な広い観察・比較も使い、[仮説を作る](#仮説を作る)手順で、既知の根拠、未確認の前提、今回試す候補を整理する。
2. **深掘りする対象を選んで試す。** 改善や理解につながる見込みと実行負担から対象を選び、下の行動選択に沿って調査・比較を具体化する。
   複数仮説の特徴量を共同で評価できる。個別作業は一件ずつ進め、問い・条件・結果をrunへ残す。
3. **事実から全体の見立てを更新する。** 結果と原本を確認し、モデルを変更した場合は性格把握も更新する。
   採否に加え、何が分かったか、他の仮説の前提・優先度や未探索の方向がどう変わるかを考える。
   期待した改善がなかった結果も、観測と解釈を分けて見立てへ反映する。
4. **広い探索へ戻る。** 更新した見立てから候補を追加・修正し、残り時間と終了条件を確認して次の深掘りを選ぶ。
   判断は履歴へ記録し、[既存state](references/state.md)の現在の結論・個別作業・次の行動を揃える。

深掘りで得た事実を次の広い探索へ戻し、この循環を繰り返す。確認済みの観察や比較は再利用する。

## 調査・比較の行動を選ぶ

改善目的と作った仮説に合わせて、次の行動を選ぶ。

- **特徴量で仮説を表現する。** 仮説から表現したい情報を考え、次にそれを特徴量でどう表現するかを設計する。
  この過程でモデルアルゴリズムの性格と現在のモデルの診断を考慮し、[特徴量設計](../feature-design/SKILL.md)で候補を具体化する。
- **EDAで基本的な全体像をつかむ。** [EDA](../eda/SKILL.md)は、分布・欠損・項目間の関係・時間や集団による違いなどを広く見て、
  仮説の前提、見落とし、新しい着眼点を得るためにも使う。「モデリングのためにデータの基本構造を理解する」こと自体を目的にできる。
  既存の概観は再利用し、仮説の具体化や誤差の背景を知りたい場合は、その問いを深掘りする。
- **特徴量設計中は設定を概ね固定する。** 仮説と表現の比較を先に進め、[パラメータ調整](../parameter-tuning/SKILL.md)は
  特徴量の構成が落ち着いてから行うことを基本とする。設定上の問題や相互作用が比較を妨げる場合は、理由を記して先に調整できる。
- **誤差分析は期待する成果から選ぶ。** [誤差分析](../error-analysis/SKILL.md)は、改善の余地や新しい仮説を見つけるために使う。
  求める性能を満たした後の深掘りも、改善による成果と、実行・確認・反映の負担で判断する。

EDAと誤差分析の範囲は、得られる理解や改善の価値と実際の負担から決める。
エージェントによって調査負担が下がる場合は、人手なら見送っていた広い観察や深掘りも候補にする。
各回の目的と区切りを持ち、残る計算費用や利用者の確認負担も含めて判断する。

選んだ行動には仮説の根拠と確かめたいことを添え、runへ残す。

## 今回の探索を区切る

合意した終了条件を満たした、時間・計算予算の上限に達した、追加試行の根拠や価値が乏しい、
または入力・利用者判断の不足で進められない場合は、理由を残して報告へ進む。
新しい試行の前に残り時間を確認し、実行・結果確認・報告まで収まる範囲を選ぶ。
実行中の処理が残る場合は、進捗と再確認方法をrunへ保存し、stateから参照する。

時間による区切りと、候補の採用・全体目標の達成を別に判断する。未評価の候補は未確認として残し、現行維持でも終了できる。
達成状況・停止理由・再開時の次の行動は既存stateへ反映する。最終評価は上のデータ利用方針に沿って実施の要否を判断する。

## 結果を返す

現在の性能と実装・運用の負担、入力の使われ方、得意・不得意、説明仮説と未確認事項をまとめる。
負担は確認できた値・条件を記し、未測定の費用を特徴量数だけから推定しない。
各runに入力・モデル・コードの版、特徴量定義、分割、設定、環境、予測と診断の原本を残す。
データの利用履歴、AVの所見、最終評価・再評価を行った場合はその判断根拠と各回の結果も報告する。
採用中の構成と基準からの変化、主要な試行で見立てが変わった根拠、停止理由と未達・未確認の範囲をまとめる。
[共通の執筆方針](../analyze/references/deliverables.md)と[雛形](assets/report.md)で、改善結果と現在地を `output.md` に統合する。
各試行の詳細は履歴・runへつなぎ、報告とstateの達成状況・次の行動を揃える。
