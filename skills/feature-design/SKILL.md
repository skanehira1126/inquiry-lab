# 特徴量の選択・設計

現行の特徴量を維持するか、どの特徴量集合・生成方法へ変更するかを判断する。
全体の進行は呼出元が担当し、依頼・run・履歴には `analyze` の共通手順を使う。
このSkillは依頼された範囲の比較と推奨を返し、委任された範囲で採否を判断する。
パラメータだけの変更は `parameter-tuning`、予測の誤差診断は `error-analysis` を使う。

## 入力と判断基準

既存の依頼・コード・結果から次を揃え、判断に必要な未決事項を確認する。

- 基準モデル、現行特徴量の定義・生成コード、予測時点と入力の利用可能時点。
- データの版・対象・分割規則、train・valid・pretest・testの利用可能な区分と利用履歴。
- 削減・追加・変換の範囲、固定パラメータと再調整の可否、候補数や時間の上限。
- 主指標、許容性能低下・同程度と扱う範囲、性能改善を目的とする場合の必要改善幅、表現を選ぶ基準、選定の委任範囲。

基本は同じ検証条件での性能とモデル入力列数を比べる。取得費・生成時間などは案件の制約に応じて加え、
列数から費用を推測しない。予測時に同じ定義で再現できることを候補の前提とする。
モデルが成熟すると、既存の複数特徴量の組合せが、新しい特徴量で表したい情報をすでに捉えている可能性がある。
追加時の改善幅だけで表現の価値を決めず、性能が同程度なら、採用順によらず仮説の根拠と表現の意図から選ぶ。
意図した特徴量が追加または置換後に使われることを、その判断材料にできる。
依存が減った既存特徴量があれば、両者が表す仮説と根拠、入力依存の変化、処理負担を比較する。
使われたことは予測への利用の証拠として扱い、仮説の正しさや性能向上とは区別する。
表現を選ぶ理由は、時期・集団を変えたときの安定性、不要な代理情報への依存の低下、少量データでの学習、
欠損・測定誤差への強さ、定義・運用の簡素さなど、期待する性質として具体化する。
採用判断を左右する性質を選んで比較し、確認済みの利点と未検証の期待を分ける。全項目の検証は要求しない。
「同程度」は案件の許容差と観測されたばらつきに照らし、結果を見て都合よく広げない。
実行前に[共通のデータ利用方針](../modeling/references/data-usage.md)を読み、呼出元から今回の利用範囲と履歴を引き継ぐ。

## 手順

1. **比較条件を揃える。** 基準と候補の評価対象・分割・指標を揃え、最初はモデル設定を固定する。
   学習を伴う補完・変換・選択は各学習部分で行う。目的変数による符号化や時系列の結合は
   [比較設計](references/comparison.md)に従い、学習行自身の正解や予測時点より後の情報を混ぜない。
2. **変更候補を作る。** 呼出元の仮説を受け取り、不足する場合は[仮説生成](../modeling/SKILL.md#仮説を作る)の手順で補う。
   まず仮説から表現したい情報と根拠を整理し、次にそれを特徴量でどう表現するかを設計する。
   この過程でモデルアルゴリズムの性格（学習・予測の仕組み、捉えやすい関係）と現在のモデルの診断を考慮する。
   表現したい意味と必要な粒度に合わせ、条件ごとに異なる生成・集計定義や、複数段階の変換・集計・結合も候補にする。
   中間処理単独の性能改善を求めず、完成した表現で意図した情報を渡せるかを考える。
   削減では除外する列・群、追加・変換では生成式・窓幅・利用時点と、その表現を選んだ理由を記す。
   複数の仮説から作った特徴量を一つの候補集合にまとめ、モデルが非線形な相互作用や補完関係を利用することも期待する。
   各仮説・特徴量群の単独効果を、候補集合へ含める前提にしない。
   データの基本的な全体像が不足していればEDAで広く把握し、仮説の具体化や誤差の確認には目的に合う探索を選ぶ。
   入力依存は[models-understanding](../models-understanding/SKILL.md)の方法から選び、
   importance・SHAPを使う場合は[重要度の読み方](references/importance.md)を参照する。相関や同じ由来の特徴量も考慮する。
3. **候補集合を再学習して比較する。** 今回試す候補全体を含む構成を基本として、基準モデルと比較する。
   候補の特徴量一覧・生成コードを保存し、性能差と列数の増減を測る。
   特徴量の分布や2値分類のROC・較正をPythonで描くときは、[inquiry-lab-api](../inquiry-lab-api/SKILL.md)で対応する関数を確認する。
   個別の比較は、候補全体から一部を削る判断や小幅なパラメータ調整に使う。
   [候補集合の比較](references/comparison.md#候補集合を比較して絞る)に従い、選んだ構成全体を再学習して当初の基準との差も確認する。
   意図した特徴量への依存と、既存特徴量への依存がどう変わったかも確認する。
   既存の表現との重複が考えられる場合は、[置換比較](references/comparison.md#表現が重なる候補を比べる)も選択肢にする。
4. **次の行動を決める。** 上の採用基準に照らして採用・見送り・保留を選ぶ。
   設定との相互作用やばらつきが判断を左右する場合は、比較設計の追加診断を予算内で選ぶ。
   委任されていないトレードオフは、性能差と入力・処理の負担を利用者に示す。

## 終了条件

依頼された比較に答えられた、追加試行の価値が低い、または予算に達したら、推奨・判断と残る証拠不足を返す。
開発比較の依頼は、候補を支持する結果が得られた場合もそこで完了する。
testの評価・再評価を依頼範囲に含む場合は、共通のデータ利用方針の進行条件と固定事項に従う。
期待以下の結果も保存して今回の依頼を閉じ、継続・再開の判断へ利用履歴を引き継ぐ。

## 出力

[レポート雛形](assets/report.md)でrunの `result.md` に比較結果をまとめる。
委任時は割当runを返し、全体の履歴・state・`output.md` は全体進行担当が更新する。
単独実行では担当者が共通記録を更新し、複数runの結果を同じ雛形で `output.md` に統合する。
執筆には[成果物の共通方針](../analyze/references/deliverables.md)を使い、次の5章で変更意図・比較結果・判断をつなぐ。

1. **結論：** 目的、特徴量集合・生成方法の変更または現行維持・保留、決め手、重要な限界を示す。
   特徴量一覧・生成コード・モデルの版を特定し、今回のtest評価・再評価の実施有無と理由、過去の利用履歴を記す。期待以下の結果も含める。
2. **性能と特徴量数の比較：** testの結果があれば先に示し、開発結果とは表を分ける。
   表には評価対象・構成とモデル版、主指標・単位、基準との差と改善方向、入力列数と増減、パラメータ変更、基準への適合・採否を載せる。
   許容差・適用した改善幅と実測差を対応づけ、列数の数え方を記す。変更を重ねた場合は当初の基準からの累積差も示す。
   費用・安定性などを評価した場合は測定条件・値・基準を添える。
3. **特徴量の変更方針と検証：** 入力・予測時点、使用した区分・分割、基準と探索範囲・予算、判断基準と判断者、
   学習部分内の処理・利用時点・評価対象・乱数を共通条件としてまとめる。
   「仮説と表現の候補」では経験・業務知識・観測のどこから仮説を立てたか、表現したい情報、モデルアルゴリズムの性格を踏まえた生成方法の選択理由を示す。
   共同で評価した候補集合と、そこから除いた列・群、設定調整を記し、構成全体の効果と個々の仮説について分かったことを区別する。
   入力依存を調べた方法・説明条件と結果を添える。importance・SHAPは[重要度の読み方](references/importance.md)に従う。
   依存が減った既存特徴量があれば、新しい特徴量との関係を示す。性能が同程度で採用する場合は、表現を選んだ根拠と確認した利点・未検証の期待を記す。
   主要な変更ごとに観測、変更した列・生成方法と意図、固定条件、再学習の結果、反証、採用・見送り・保留を対応づける。
   再調整した場合は基準と候補の探索条件を示し、固定設定での比較と分ける。
   testへ進んだ根拠と固定構成・再学習手順、または評価せず終えた理由を記す。
4. **適用範囲と残る課題：** 対象・期間・入力の取得条件、未確認条件、残る選択、停止理由を示す。
   追加改善は次の分析候補とし、データ利用履歴と再開に必要な条件を引き継ぐ。
5. **参考：** 依頼、作業履歴、特徴量定義、候補別結果、生成・選択・学習コードへの入口をまとめる。

各runから全特徴量の定義・依存元・利用時点、入力・コードの版、分割、設定、乱数、環境、結果を辿れるようにする。
