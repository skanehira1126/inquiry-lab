# EDAの依頼と返却

`eda-loop` などの呼出元と、1shotを実施する `eda` が共有する契約。
依頼文や既存文書への参照で以下が分かればよく、専用JSONや新しいCLI入力形式は要求しない。
利用者が `eda` を単独で使うときも、独立したサブエージェントへ渡すときも同じ内容を使う。
`eda-loop` からの依頼は毎回新しい子へ渡すため、この契約と参照先だけで今回の観察を始められるようにする。

## 呼出元が渡す情報

| 情報 | 渡す内容 | 未定・初回の場合 |
|---|---|---|
| 今回の関心と探索範囲 | 全体像の把握か、特定の現象の探索か。対象・期間・観測単位、既知の不足と今回見る理由。利用意図はあれば添える | 個別の仮説は不要。指定がなければ広い視点からデータを説明することを出発点にする |
| 入力と利用条件 | データの場所・版・取得日、定義と生成手順への参照、読める範囲・禁止範囲、探索や最終評価での使用歴 | 不明な定義は不明とする。入力や利用範囲が特定できなければ、その部分の探索は始めない |
| 関連する既知の観測 | 調査済み範囲と方法、主要な観測・原本、説明候補、反証・限界、未確認の点 | 初回は「既存の観測なし」でよい。前回の結論だけでなく、今回必要な根拠を添える |
| 固定条件と裁量 | 必ず守る比較条件・除外規則・禁止操作。方法の提案があれば、必須条件と分ける | 指定がなければ、許可された範囲でEDAが見方と方法を選ぶ。期待する結論や仮説の個数は固定しない |
| 実行条件と予算 | 利用する環境・既存コード、時間・計算量の上限、報告に残す時間 | 既存環境から分かることは参照で渡す。上限が未定なら、実施前に依頼に見合う範囲を定める |
| runと返却先 | ワークスペース、runラベル、依頼文書への参照、`result.md` と成果物の保存先、新規か中断再開か | 呼出元がinitまたはrun newで保存先を準備し、返されたパスとrunラベルを渡す。CLIが使えない場合はanalyzeの共通手順に従う |

使う入力と根拠は、別コンテキストからも辿れるパス・URLと版で示す。相対パスなら基準ディレクトリを指定する。
会話を丸ごと渡す代わりに、今回の判断を変える観測・反証・制約を選ぶ。探索履歴を省いて未使用データに見せない。
モデルの診断結果から依頼する場合も、観測された誤差と、その説明候補を分けて渡す。

## EDAが受け取って決めること

渡された依頼と参照先を確認し、データを説明するための暫定的な質問と具体的な観察計画を選ぶ。
呼出元は関心と範囲を定め、EDAはその範囲内の集計・図・比較・事例の選び方を具体化する。
方法まで指定されている場合はその意図と必須性を確認し、異なる方法が必要なら理由を示す。

不足を既存資料から補えるなら補い、依頼元からの情報と自分で確認した事実を区別してrunへ残す。
結論に影響する意味・利用範囲の不明点や矛盾は推測で埋めず、呼出元へ確認する。
確認できない場合は影響する項目を保留し、実施できた範囲と不足を返す。
サブエージェントは新たな探索範囲や予算の拡大を自分で決めない。

利用者が `eda` を直接呼ぶ場合も、この情報を依頼と現物から整理する。全項目を質問票として尋ねる必要はない。
保存先が未準備ならanalyzeの共通手順で用意し、割り当てたrunへ保存する。
新規の分析先には `inquiry-lab init <分析先> --title "分析タイトル" --template eda` を使う。
既存の分析先へ追加する場合は、
`inquiry-lab run new --workspace <分析先> --title "今回のEDAのタイトル" --template eda` を使う。
番号はCLIが割り当てる。返された保存先とresult.md内のrunラベルを使い、事前に次の番号を決め打ちしない。
初期依頼以外を参照する場合は `--request <依頼文書>` を付ける。相対パスは分析先を基準にする。
委任時は呼出元が保存先を準備し、子は作成済みrunへ記入する。再開時や、汎用雛形がすでにあるrunでは
作成コマンドを再実行せず、既存内容を保ってEDAの構成へ整える。
`init` が作る `output.md` の雛形は統合結果として扱わず、EDAは今回のrunを仕上げて返す。

## runとして返す情報

出力は `runs/<番号>/result.md` と、そのrunの成果物を基本とし、呼出元が指定した配置を使う。
[EDAのrun結果雛形](../assets/result.md)を使い、初期雛形を今回の説明に整える。既存runを再開する場合は記録済みの内容と参照を保つ。
本文は今回の観察の位置づけ、対象と方法、観察結果と読み取り、今回言えることと限界、参考・再現情報の5章とする。
観察のまとまりごとに対象・条件、図表や数値、読み取り、留保を近くに置き、今回の根拠を確認できるようにする。
既存の理解への影響や重要な未回答事項は本文に残す。質問別の回答の対応、次の候補と完了状況は付録の作業記録に置く。
実行前に質問と計画を残し、実行後に回答と本文・原本への参照を追記する。
呼出元はこの記録で確認範囲を照合するが、統合レポートへ質問一覧を転記しない。

- **依頼・実施範囲**：runラベル、依頼への参照、今回の関心、入力版と実際に読んだ範囲。
- **計画と実施状況**：暫定的な質問、選んだ理由、方法・比較条件、各質問への回答と根拠または未実施・評価不能の理由。準備で確認した実例の範囲も含む。
- **観測と根拠**：件数・分母・単位を含む主要な値や図、コード・コマンド・環境・パラメータと保存した原本への参照。
- **解釈と仮説**：得られた理解、説明候補、重要な反証・限界。既知の理解が維持・変更された点。
- **次の候補**：説明に不足する視点、修正・追加したい質問と理由、次に必要な証拠・条件。当初の計画と区別し、追加探索やモデル変更は提案とする。
- **完了状況**：計画の完了または中断・制約による区切り、再開条件、呼出元の統合結果へ反映すべき点。

「計画した観察を完了した」「傾向が見られなかった」「測定できなかった」を混同しない。
対話での返却には、結果と成果物の場所、重要な知見・制約を短く添える。保存できなければ理由と未保存の内容を明示する。
EDAは `output.md` を執筆・更新せず、分析全体の採否・継続判断を確定しない。
委任時の依頼文書・共有履歴・統合レポートの更新は呼出元が担う。直接実行時は共通手順でrunを履歴へ記録できる。

## 依頼の短い例

以下は架空の依頼例。固有の列や数値を共通の要件にはしない。

> 関心は、イベント間の構成差に隠れた分布の違いを見つけること。
> 今回は指定期間の参加記録を対象にする。入力・版・定義・読める範囲は指定の入力一覧を参照。
> 前回runでは全体の分布に複数の山を観測した。群の混在は説明候補で、未検証。該当図と集計を渡す。
> 期間と欠測の扱いは前回と揃える。イベント内外の比較は方法の候補で、具体的な図や集計は任せる。
> 報告を含め30分を上限とし、既存環境を使う。
> 割当済みのrunのresult.mdとartifactsへ保存し、観測・仮説・反証・次の候補を返す。追加探索は実行しない。
