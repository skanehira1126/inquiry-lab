# 分析レポートと作業history

分析レポートは、判断する人が問いへの現在の答えを読むために使う。作業historyは、別の人が途中から引き継いでも、何を試し、どの根拠で方針を変え、どこで止めたかを辿れるようにする。どちらも同じ試行（run）と保存済みの根拠を参照する。

## レポートの共通方針

レポートの目的は、分析の知見を伝え、生成AIが結論に至った判断を利用者が効率よくレビューできるようにすること。
テーマ別スキルが持つ出力レポートの雛形を使い、そのテーマ内では大章の名前と読み順を固定する。
小見出しや段落は、案件の結論と、それを支える判断に合わせて組み立てる。

冒頭に目的、結論、決め手、重要な留保を置く。本文の説明順はテーマの判断過程に合わせる。
たとえばチューニングでは、観測したデータの性質や診断結果から調整を選び、検証結果から判断する流れを示す。
結論から主要な判断とその証拠・条件へは、見出しと本文内の参照で辿れるようにする。
結論を成立させる各判断について、何を観測し、どの基準や前提を使い、なぜそう解釈したかを本文で確認できるようにする。
詳しい計算や実行条件は各ループの詳細へリンクし、再現用の原本に辿れるようにする。

見送った分岐は結論への影響に応じて短く触れる。棄却した仮説、棄却理由、結論への影響が分かれば、
その検証の全経過を展開する必要はない。一方、候補の除外や探索範囲の選択が最終結論を左右する場合は、
その判断も根拠とともに説明する。支持する証拠と矛盾する重要な観測、比較条件の変更、
結論を変えうる不確実性は対応する判断の近くに残す。

条件や複数の観測は箇条書き、同じ軸の数値比較は表、解釈は短い文章で示す。
図表には対象・単位・比較条件と読み取るべき点を添える。
リンク名は「店舗別の欠測確認」など内容を表す言葉にし、run IDは参照先で確認できるようにする。
主張から根拠へ直接進めるよう、参考文献一覧に加えて本文の該当箇所にも参照を置く。

テーマ別の雛形がない場合は「概要」「対象・方法」「結果・考察」「残る課題」「参考」を起点に、
上の目的を満たす構成を案件ごとに選ぶ。

## 作業historyの共通部分

人が読む `作業履歴.md` では、冒頭に目的・依頼・当初の判断基準への参照と「現在地」を置く。現在地には記録済みの判断、停止理由または次の作業と該当記録へのリンクを示す。続く「試行履歴」には古い順に、試行の題・短い要約・詳細へのリンクを並べる。試行を伴わない基準変更や利用者判断も、その時点と理由が分かる位置に加える。

履歴に表示する `summary` には、何が分かり、どう判断したかを1〜2文で記す。仮説の検証手順や数値の一覧は各ループの詳細へ置く。要約のない既存の記録は `current_state` を表示する。

各ループの詳細は、同じJSONから `history/NNNNNN.md` に生成する。次の5項目を見出しとして、内容を箇条書きにする。判断が不自然に見えるときに、証拠・判断基準・理由をここで確認できるように残す。

- **仮説**　何を判断したくて、この試行を選んだかを書く。事前の見立てがあれば添える。EDAでも「何を調べるか」と「それが分かるとどの判断に役立つか」を結びつける。
- **検証**　実際に使った入力の版・範囲、比較条件、手順。再現に必要なパラメータや環境、予定との差を含める。
- **結果**　観測した値や図表から読み取れる事実。失敗・中断時はどこまで実行でき、何が未測定かを書く。
- **考察**　結果を判断基準に照らしてどう解釈したか。そこから選んだ次の試行、停止理由や再開条件を記す。
- **参考**　結果の出典や検証手順を辿れる参照。CSVは対象行、図は内容、MLflowはrunと指標名など、リンク先の何を見るかを添える。

JSONの項目とCLI操作は[履歴JSONの記録手順](history-recording.md)を参照する。
分析先の `history/` に保存したJSONから、短い履歴と各ループの詳細を一度に再生成する。
分析レポートの `output.md` は、この履歴や該当するrunの結果を参照する。

過去のrunの設定・入力・集計から派生する場合は、その記録の `sequence` を `base_run` に指定する。試行が行き詰まって以前のrunに戻る場合も、戻り先を明記する。別の試行結果や判断を今回の前提に使ったら、その記録の `sequence` を `depends_on` に列挙する。図で作業内容が分かる短い `title` を添える。履歴の冒頭に依存元から今回の記録への矢印が表示される。単に実施順が前後しただけの記録は結ばない。

## 保存した根拠の参照と掲載

- **原本を特定する。** ローカルの画像やCSVには参照元の文書から解決できる相対リンクを使う。ワークスペース外なら保存場所と版を記す。MLflowでは対象のtracking先、run IDと、画像・CSVのartifact内のパス、または指標名と必要に応じてstepを記す。読者が開けるrunリンクがあれば添える。分析のrunとMLflowのrunの対応はhistoryに残す。
- **本文に必要な量を選ぶ。** その根拠を開かなければ結論や重要な留保が分からない場合、値と単位、CSVの該当行の要約、または読み取る点を添えた図を本文に載せる。全件のCSV、探索中の全図、詳細ログはhistoryから原本を参照する。レポート掲載分にも対応するrunと原本への参照を添える。
- **配布先で辿れるか確かめる。** ローカル限定の図や認証が必要なMLflowの図は、必要に応じて共有可能な抜粋や図を `report/` などへ用意し、レポートからリンクまたは埋め込む。キャプションに対象と原本との対応を残す。原本が閲覧できない場合は、その制約と確認できた範囲を明記する。

たとえばMLflowに検証結果を保存した場合、historyには「分析run-002／社内trackingのMLflow run `<run_id>`／指標 `valid_auc` のstep 3は0.75／図 `plots/roc.png`」と記す。レポートには「検証AUCは基準の0.72から0.75に上がった」と比較条件を添え、run-002と元のMLflow runにリンクする。曲線の形が判断を左右するなら、本文にも該当する図を掲載する。

## テーマ別の出力レポート

テーマ別スキルに `assets/report-template.md` を同梱し、総評を作る段階で参照する。
大章の役割と読み順、可変の小見出しの作り方、本文に必要な値・図表、詳細へ参照する情報を定める。
[パラメータチューニングの雛形](../../parameter-tuning/assets/report-template.md)は、
結論、性能と診断、調整方針と検証、適用範囲と課題、参考を大章とする。

- **必須**の内容は、根拠がないときも未測定や判断保留とその理由を示す。
- **条件付き**の内容は、指定条件を満たせば掲載する。該当なしが判断に関わる場合は
  「最終評価は候補見送りのため未実施」など理由を明記する。
- **任意**の内容は、理解や判断を変えるときに選ぶ。全試行の経緯は作業履歴から辿れるようにする。
